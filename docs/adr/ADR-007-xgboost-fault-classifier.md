# ADR 007 – XGBoost Fault Classifier for ml‑service (W7)

**Status:** Accepted  
**Date:** 2026-10-14  

## Context
The NOC AIOps demo (NetSentinel) requires a lightweight, deterministic fault‑type classifier that can run inside a 256 MiB container. The existing rule‑based approach cannot scale to the 29 numeric features derived from enriched alarms (severity, one‑hot node type, topology blast radius, dedup count, KPI context, alarm‑group size, etc.). A synthetic data set generated by `synth_faults.py` provides labelled fault types for training and evaluation.  

## Decision
We integrate an XGBoost (CPU) model (`xgboost-cpu`) into `ml-service` (FastAPI, port 8003) as the primary fault classifier.

* **Features:** 29 numeric columns extracted from the enriched alarm payload.  
* **Leakage protection:** Root‑cause labels (`LEAKY_FIELDS`) are stripped from the feature vector; a unit test validates that no leakage occurs.  
* **Training pipeline:** `make ml-train-xgb` runs `python -m ml_service.train_xgb --register`. The script consumes the synthetic fault data, performs a time‑based split (earlier alarms → train, later alarms → test), and registers the model in the local registry (`models/registry.json`).  
* **Model storage:** Model artefacts are written to `MODELS_DIR` (default `models`; compose sets `/tmp/models`). The registry is a simple JSON file; MLflow integration is optional per ADR‑006.  
* **Runtime selection:** The environment variable `MODEL_NAME` selects the registered model name (latest version is loaded on first use).  
* **Auto‑training:** If `AUTO_TRAIN=1` (default) and no model is present, a minimal synthetic model is trained on first request. Setting `AUTO_TRAIN=0` disables this behaviour; `/predict` and `/explain` will return HTTP 503.  

**Explanations:** SHAP values are generated using XGBoost’s built‑in TreeSHAP (`Booster.predict(pred_contribs=True)`). No external `shap` package is installed, saving ~100 MiB.  

## Consequences
* **Performance:** XGBoost inference fits comfortably within the 256 MiB limit; TreeSHAP contributions are computed on‑demand for the top‑k features (default 5).  
* **Maintainability:** The model lifecycle is managed via a JSON registry; no external tracking server is required.  
* **Testing:** Synthetic evaluation (n = 3000, seed 42) yields accuracy ≈ 0.84 and macro‑F1 ≈ 0.84. The data generator is seeded; the time‑based split mirrors deployment (train on the past, predict the future) and avoids optimistic random-split leakage.  
* **Limitations:** The model is trained on synthetic data only; it must not be presented as a production‑grade predictor for real networks.  

## Alternatives considered
1. **Deep‑learning classifier (PyTorch/TensorFlow).** Rejected due to memory footprint (>256 MiB) and longer cold‑start times.  
2. **Rule‑based scoring engine.** Insufficient expressiveness for the 29‑dimensional feature space and unable to provide SHAP‑style explanations.  
3. **External MLflow model registry.** Deemed unnecessary complexity for a demo; the local JSON registry meets the requirements.
